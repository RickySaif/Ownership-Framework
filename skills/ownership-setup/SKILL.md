# Ownership setup

You are setting up a **QA hub** for someone who may not be a programmer. Be friendly, use plain words, and ask
**one short question at a time**, always with a sensible default they can accept by saying "yes" or pressing enter.

## 1. Interview

Follow `interview.md` (next to this file). It lists every question, its default, and what to do with the answer.
Collect the answers into an `answers.json` (format: `examples/acme-leave/answers.json` in the framework).

Rules while interviewing:
- **Never ask for a password or token in the chat.** When an account or token is needed, tell the user how to put it
  into the OS keychain themselves (see `templates/hub/accounts/README.md`), and record only the reference
  (`{ "keychain": "qa-hub/<app>/<role>", "env": "<APP>_<ROLE>_PASSWORD" }`).
- Test accounts must be made for testing (synthetic). Never use a real person's account.
- If they don't know an answer (for example the database host), use the default or leave that environment out. It
  can be added later by editing `registry.yaml`.
- Production: the default is "read-only smoke on synthetic accounts". Only record an exception if they name who
  approved it, the scope and an end date.

## 2. Generate the hub

```sh
node <framework>/skills/ownership-setup/scripts/generate-hub.mjs --answers answers.json --out <hub-folder>
```

`<framework>` is where this plugin lives (the folder that contains `templates/hub`). Then, in the hub folder:

```sh
git init && git add -A && git commit -m "QA hub generated by ownership-setup"
npm install
npm run init        # installs and checks Playwright, browsers, Playwright MCP, Graphify, ffmpeg, DB clients
npm run sync        # downloads each app (tip of its branch) into apps/, read-only, and builds the code graph
npm run smoke       # the generated login smoke spec, one per role
npm run board       # board/index.html
```

`npm run init` asks before installing anything. Explain each step in one line as it runs. If a step fails, say what
it means in plain words and how to fix it, then continue with the rest.

## 3. Show the result

- Say what was created (the hub layout from the generated README), where the board is, and what the smoke run said.
- If smoke failed on login, the usual cause is a missing keychain entry or a wrong login selector in
  `registry.yaml` → `login.ui`. Help fix it, then rerun `npm run smoke`.
- Suggest next steps based on their choices: `smoke-spec` (one core flow per role), `spec-assurance` (turn the
  requirements into checks), `exploratory-hunt`, and `routine-setup` for nightly and weekly runs.
- Offer to push the hub to a **private** repo. A hub holds evidence about apps; it should not be public.

## Updating a hub later

When the framework has new tools, run the generator with `--update`. It refreshes framework files (tools, lib,
schemas, board template, configs) and never touches bugs, specs, runs, notes, `registry.yaml`, `CLAUDE.md` or the
playbook.
